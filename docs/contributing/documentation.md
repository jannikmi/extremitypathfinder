# Documentation

The documentation is built with [Sphinx](https://www.sphinx-doc.org/) and hosted on
[Read the Docs](https://extremitypathfinder.readthedocs.io/).

## Building

```sh
make docs              # HTML in docs/_build/html
uv run tox -e docs     # the strict build of CI: warnings are errors
```

## Formats

- The user documentation (`docs/*.rst`), `README.rst` and `CHANGELOG.rst` are reStructuredText.
- The contributing guide (`CONTRIBUTING.md`, `docs/contributing/*.md`) and `AGENTS.md` are Markdown,
  rendered by [MyST](https://myst-parser.readthedocs.io/). `docs/5_contributing.md` includes `CONTRIBUTING.md`.

## Links in the contributing guide

The Markdown files are read on GitHub and in the HTML documentation, so links must work in both:

- Link to other pages of the documentation with relative paths, e.g. `[Testing](testing.md)` or
  `[Engineering Design](../8_design.rst)`.
- In `CONTRIBUTING.md`, link to documentation pages with paths starting with `docs/`
  (rewritten when the file is included in the documentation).
- Refer to repository files outside of `docs/` as code (`` `scripts/release.py` ``) or link them with an absolute
  GitHub URL. Relative links outside of `docs/` break in the documentation build.

## Content

- Document changed behaviour in the same pull request: the usage page, docstrings (the API page is generated from them),
  and the README if its example or feature list is affected.
- No measured numbers in static pages (README, the pages under `docs/`, docstrings, comments): timings, speed-ups,
  sizes, counts of tested inputs and the like go stale. Describe the result qualitatively (e.g. "within the noise",
  "much faster") and refer to the issue or pull request with the measurements. The numbers belong there (cf.
  [Performance](performance.md)), in the changelog entry of a release (a record of that release) and in the
  rendered benchmark pages (tables and figures), which are generated again with every full run and carry exact numbers.
  The same holds for other exact figures (supported versions, ...): refer to their source (e.g. `pyproject.toml`).
  Mark text derived from the benchmark results, so that it is updated with them
  (cf. [After a full run](performance.md#after-a-full-run)).
- The figures in `docs/_static` and the demo image of the README are generated by `scripts/docs_figures.py`
  from actual results of the package. Regenerate them when a change affects them:

  ```sh
  uv run python scripts/docs_figures.py
  ```

  The exports are deterministic: regenerating them without changes yields identical files.
- The world map figure (`docs/_static/demo_world.svg`) is not part of the above: it is generated by the standalone
  `scripts/world_demo.py`
  from the simplified Natural Earth map of the benchmarks (needs the `benchmark` group and a download of the data):

  ```sh
  uv run --group benchmark python scripts/world_demo.py
  ```
- The benchmark documentation has three pages for three kinds of readers: the results (users),
  the method (reviewers of the numbers) and running them (contributors, in this guide).
  Speed and memory stay on one page, because they are read side by side,
  and the pyvisgraph defects stay next to the validation that found them (#165).

## Size and structure of this guide

Each page of the contributing guide is read in full by humans and loaded into the context of coding agents,
so it stays short. `scripts/check_contributing_guide.py` (pre-commit and tests) enforces two rules,
configured in the `[tool.contributing-guide]` table of `pyproject.toml`:

- **Word limit:** a page in `docs/contributing/` has at most `max-words` words (1000), counted like `wc -w`.
  A page may exceed it only with an exception in that table that states the reason, e.g. a table or procedure
  that is clearer in one piece. The check rejects exceptions without a reason
  and exceptions for pages back within the default limit.
- **Reachability:** every file in `docs/contributing/` can be reached from `CONTRIBUTING.md` (`entry-points`)
  by following links through the pages of the guide. Pages linking only to each other are not enough,
  and references from elsewhere (the hidden toctree in `docs/5_contributing.md`, other documentation pages, skills)
  do not count: a reader starting at `CONTRIBUTING.md` must find every page.

When editing the guide:

- **Amend instead of append.** Update the rule, sentence or section that covers the topic, merge duplicates and
  delete what stopped mattering. Add a new section only for a new topic.
- **Condense before splitting.** When a page reaches the limit, first review whether it can be condensed without
  losing significant information: merge duplicates, drop outdated or obvious rules, tighten the wording.
  Information covered elsewhere (another page, `AGENTS.md`, docstrings, the code, an issue) can be dropped,
  with a link to it where readers need it.
- **Split what remains.** If the page is still too long, split it along its topics or readers into pages that can
  be read on their own (e.g. a procedure and its reference), not into numbered parts. Link the new pages from
  `CONTRIBUTING.md` or a page reachable from it (and from `AGENTS.md` if agents need them), add them to the toctree
  in `docs/5_contributing.md` and update the links to moved sections.
